# ScreenpipeMenu — macOS Menu Bar App Design

**Date:** 2026-05-11
**Status:** Approved — ready for implementation

## Goal

A self-contained macOS menu bar app, written in Swift, that runs the screenpipe recorder automatically while the app is open. Distributable as a single `.app` bundle that the author's coworkers can run by double-clicking — no Node.js, no Terminal, no manual setup.

## Decisions (locked)

| | |
|---|---|
| UI style | Menu bar only (no Dock icon, no window). `LSUIElement=true`. |
| Binary delivery | Download-on-first-launch from npmjs.org registry (per-arch tarball). |
| Lifecycle | Quitting the app stops the recorder (SIGTERM → SIGKILL fallback). |
| Signing | Unsigned, ad-hoc codesign for local execution. README documents Gatekeeper bypass. |
| Pause/resume | Two separate items: "Pause audio" uses screenpipe API; "Pause screen" stop/restarts the recorder process. |

## Architecture

Single Swift Package Manager executable, assembled into a `.app` bundle by a build script.

```
ScreenpipeMenu.app
├── Contents/
│   ├── Info.plist                  (LSUIElement, usage strings, bundle id)
│   ├── MacOS/
│   │   └── ScreenpipeMenu          (universal binary, arm64 + x86_64)
│   └── Resources/
│       └── (icon assets, if any)
```

Runtime data lives outside the bundle in:
- `~/Library/Application Support/ScreenpipeMenu/bin/screenpipe` — downloaded recorder binary
- `~/Library/Application Support/ScreenpipeMenu/version.txt` — installed version string
- `~/Library/Logs/ScreenpipeMenu/recorder.log` — child process stdout+stderr
- `~/.screenpipe/` — screenpipe's own data (unchanged from default)

## Components

**ScreenpipeMenuApp.swift** — `@main` entry. Declares a `MenuBarExtra` scene. Owns an `AppState` instance. Wires `applicationWillTerminate` to stop the recorder cleanly.

**AppState.swift** — `@Observable` class holding:
- `status: Status` enum: `.idle, .downloading(progress), .starting, .recording, .audioPaused, .visionPaused, .bothPaused, .error(String)`
- `currentVersion: String?`
- Methods: `start()`, `stop()`, `pauseAudio()`, `resumeAudio()`, `pauseVision()`, `resumeVision()`

**BinaryManager.swift** — pure logic, no UI. Responsibilities:
- `ensureBinary() async throws -> URL` — returns path to a runnable screenpipe binary, downloading if absent
- Fetches `https://registry.npmjs.org/screenpipe/latest` → reads `version` field
- Picks arch via `uname -m` → builds tarball URL for `@screenpipe/cli-darwin-{arm64|x64}`
- Downloads via `URLSession`, extracts via `Process` running `/usr/bin/tar -xzf`
- `chmod +x` the resulting binary
- Writes `version.txt`

**RecorderProcess.swift** — owns a `Process` instance.
- `start(binaryURL:)` — launches `screenpipe record` with `SCREENPIPE_API_KEY` env var set to a token we generate, captures stdout+stderr to a `FileHandle` for the log file
- `stop()` — sends SIGTERM, waits up to 3 s, sends SIGKILL if still alive
- `terminationHandler` posts `.recorderExited(code)` to `AppState`

**APIClient.swift** — thin wrapper over `URLSession` for the screenpipe HTTP API at `http://127.0.0.1:3030`:
- `health() async -> HealthStatus` — polled every 5 s while running
- `audioStop()`, `audioStart()` — POST endpoints for audio pause/resume
- All requests include `Authorization: Bearer <token>` header

## Lifecycle / data flow

```
launch
  → AppState.status = .starting
  → BinaryManager.ensureBinary()
       binary present? → return path
       absent? → status = .downloading(0%)
                 fetch version → fetch tarball → tar -xzf → chmod +x
  → RecorderProcess.start() with SCREENPIPE_API_KEY=<generated-token>
  → poll /health every 5 s
       healthy → status = .recording
       fails N times → status = .error("recorder not responding")

user clicks "Pause audio"
  → APIClient.audioStop() → status = .audioPaused (vision still capturing)

user clicks "Resume audio"
  → APIClient.audioStart() → status = .recording

user clicks "Pause screen"
  → RecorderProcess.stop() → status = .visionPaused
  → (we keep the menu showing "Resume screen")

user clicks "Resume screen"
  → RecorderProcess.start() → status = .starting → .recording when /health OK

quit (Cmd-Q, menu Quit, or app close)
  → applicationWillTerminate:
      RecorderProcess.stop() (SIGTERM, 3 s, SIGKILL)
```

The auth token is generated by the app (UUID-shaped, e.g. `sp-<8 hex>`) and passed via the `SCREENPIPE_API_KEY` env var when spawning the child. The app uses the same token for its own API calls. No on-disk token storage from our side — screenpipe will read it from the env at startup.

## Menu UI

```
●  Recording                    [status row, dot color reflects state]
─────────────
Pause audio        / Resume audio
Pause screen       / Resume screen
─────────────
Open data folder              [opens ~/.screenpipe in Finder]
Open log file                 [opens ~/Library/Logs/ScreenpipeMenu/recorder.log]
Open Privacy Settings         [opens Screen Recording pane]
─────────────
Re-download binary            [forces fresh download next start]
About ScreenpipeMenu          [version, GitHub link]
Quit                          [Cmd-Q]
```

Status row colors:
- Green ● — recording (both audio + vision active)
- Yellow ● — partial: audio paused or vision paused
- Blue ● — downloading or starting
- Red ● — error
- Gray ● — idle / stopped

The menu bar **icon itself** is an SF Symbol that changes with state: `record.circle.fill` (recording), `pause.circle.fill` (any paused), `arrow.down.circle` (downloading), `exclamationmark.circle.fill` (error).

## Error handling

Only handle errors that can actually happen:

| Failure | UX |
|---|---|
| Download fails (network / 404) | Status row shows "⚠ Download failed", menu shows "Retry download" item |
| Tarball extract fails | Same as above, log file shows tar output |
| Recorder process exits unexpectedly (non-zero code) | Status row shows "⚠ Recorder crashed (exit N)", menu shows "Restart" item, log file pointer |
| `/health` unreachable for 30 s after start | Same as above (treat as crash) |
| Port 3030 already in use | Detected via health check failing immediately; status row shows "⚠ Port 3030 in use — another screenpipe running?" |
| macOS permission denied (Screen Recording / Mic) | Not directly detectable — recorder will run but capture nothing. Menu always has "Open Privacy Settings" item to nudge the user. |

We do **not** try to auto-recover from crashes in a loop (avoid death-spirals). User clicks "Restart".

## Build & distribution

**`build.sh`** (the only build entry point — no Xcode required):

1. `swift build -c release --arch arm64 --arch x86_64` → universal binary
2. Construct `ScreenpipeMenu.app/Contents/{MacOS,Resources}/` directory structure
3. Copy the universal binary into `Contents/MacOS/ScreenpipeMenu`
4. Write `Contents/Info.plist` with:
   - `CFBundleIdentifier`: `com.mengo.screenpipemenu`
   - `LSUIElement`: `true` (no Dock icon)
   - `LSMinimumSystemVersion`: `15.0` (Sequoia — enables `@Observable` and modern SwiftUI)
   - `NSMicrophoneUsageDescription`: "Records audio to power screenpipe's transcription."
   - `NSCameraUsageDescription`: "Required for screen recording on some systems."
   - `NSScreenCaptureUsageDescription`: "Captures your screen for screenpipe's local-only memory."
5. `codesign --sign - --deep --force ScreenpipeMenu.app` (ad-hoc)
6. `ditto -c -k --sequesterRsrc --keepParent ScreenpipeMenu.app ScreenpipeMenu.zip`

**README.md** for coworkers:

```
1. Download ScreenpipeMenu.zip, unzip.
2. The first time you open it, macOS will warn:
   - Right-click ScreenpipeMenu.app → "Open" → "Open" in the dialog.
   - From then on, double-click works normally.
3. Grant the permission prompts when they appear:
   - Screen Recording  (System Settings → Privacy & Security)
   - Microphone        (same place)
   - Accessibility     (same place)
4. The app lives in your menu bar (top-right). Click the icon to see status.
```

## Out of scope (YAGNI)

- No preferences UI. Defaults are fine; advanced users edit screenpipe flags in source.
- No auto-update of the .app itself. Rebuild + reshare.
- No launch-at-login / login-item. Recording is tied to the app being open (per decision).
- No custom icon design — uses SF Symbols.
- No notification when recording starts/stops.
- No data dashboard / search UI inside the app — that's what the existing MCP / Claude Code does.

## Testing

Manual smoke test checklist (run after each meaningful change):

1. **First-launch download** — delete `~/Library/Application Support/ScreenpipeMenu`, launch app, watch menu show "Downloading…", verify binary appears in expected path.
2. **Recording starts** — within 30 s of first launch, status dot turns green, `/health` returns healthy.
3. **Pause audio** — click "Pause audio", `/health` shows audio chunks stop incrementing, screen frames still increment.
4. **Pause screen** — click "Pause screen", recorder process exits (PID gone), menu shows "Resume screen".
5. **Resume screen** — click "Resume screen", binary respawns, status returns to green within ~15 s.
6. **Quit** — Cmd-Q, verify recorder process gone (`pgrep screenpipe` returns nothing).
7. **Crash recovery** — `kill -9` the recorder externally, verify menu shows error state, "Restart" works.
8. **Coworker simulation** — copy the built `.app` to a fresh user account, right-click → Open, verify it runs and downloads on first launch.

No automated tests for v1. The app is small, the moving parts are all I/O against external systems (npm registry, screenpipe HTTP API, macOS), and unit tests would mostly be testing mocks. We re-evaluate if the app grows.
